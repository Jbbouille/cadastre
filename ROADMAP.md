# Roadmap

What is done, then what is planned, in rough order of priority.

## Done

1. Tree-sitter grammar and test corpus
2. Compiler: syntax tree → registry, name resolution (suffixes, lexical scope, kind filtering), built-in schema, consistency checks (IP / CIDR, racks, `peer`, channels), diagnostics, incomplete elements and suggestions (`cadastre check`)
3. Views `select`, `where`, `group-by`, `edges`, `lift`, `follow`, `through: show` and DOT → SVG rendering (`cadastre build`)
4. Text output, Mermaid (ELK layout, parallel links merged), ASCII art (layered layout, frames for groups, orthogonal routing); styles and default theme
5. Browser: compilation and rendering from the WebAssembly module, SVG through a WebAssembly build of Graphviz (`web/`)
6. Language server with diagnostics, semantic highlighting, outline, go to definition and hover; VS Code extension with live view preview and build (`cadastre lsp`, `editors/vscode`)
7. Playground:
   - syntax highlighting with the grammar's `highlights.scm`, through a `highlight_text` export of the WebAssembly module (the same coloring as the language server)
   - opening a local folder: its `.ca` and `.cav` files are read in the browser, nothing is uploaded
   - ad-hoc views written on the fly, highlighted, rendered instead of the selected view, with their diagnostics
8. Project and files: a project is a directory, every `.ca` / `.cav` file is compiled, no entry point nor imports between files; UTF-8 required (byte order mark ignored by the parser, invalid files reported as diagnostics at their first invalid byte)
9. Code base clean for `cargo clippy`; roadmap in its own file
10. Virtual IPs and DNS names: `vip` carried by a load balancer, a proxy or a cluster, with `host` names (a new `host` value type), `ip` and `subnet`; usable as a flow target by its host name (`-> labels.example.com`); shown in views by its host name; checks: address inside the subnet CIDR and unique, host name served by one virtual IP
11. Shared servers: `hosts` and `shared` pseudo-attributes in views, derived from `on` (`select server where shared`), and what a resource hosts in the hover
12. `group-by` follows `on`: a resource without an ancestor nor a reference of the grouping kind goes into the frame of what it runs on (an app on an ESX of a vCenter cluster)
13. Icons in SVG renderings: the icon of its kind left of the text of each node and frame (Lucide, ISC), embedded in the file; `icons: false` to remove them; in the command line, the playground and the VS Code preview
14. Styles and legends: the legend lists only the rules whose style shows in the view, with swatches (filled squares for nodes, solid / dashed / dotted lines for edges), in SVG, Mermaid, text and ASCII art; `fill` for nodes and frames (white text on a dark fill), `kind` rules on group frames (border, fill); any key of the links or connectors as an edge label (`edge_labels: [circuit_id]`)
15. Layout hints: `direction: rl | bt` (frame titles kept at the top), `stack: [...]` to order frames and nodes (invisible edges, in DOT and Mermaid), `layout: free` edges drawn without placing nodes
16. Nodes drawn as frames: a node that is also a frame of the view (a server hosting the apps grouped by `group-by … > on`) is drawn once, as the frame, with the text, style and icon of the node; edges stop at its border (Graphviz `compound`, Mermaid links to subgraphs)
17. Keys of the interfaces on `peer` cables: `edge_labels` reads the keys of the ends of a reference edge, the declaring end first, kept through `lift` (`edge_labels: [label, circuit_id]` writes the ports and circuit of each fiber); the relation name only shows when no other label applies
18. `cross: [...]`: frames and nodes ordered across the direction of the view (top to bottom in `lr`, left to right in `tb`), through the order they are written in
19. Completion in the language server: kinds, keys, closed values and referenced resources in registries (by their shortest unambiguous name, host names of virtual IPs as link targets), protocols and layers of the project; keywords, kinds, formats, render options and style properties in plans
20. Find references and highlighting of the occurrences of a name: the declaration of a resource and every name that designates it, in the registry and the plans, names of `where` filters included
21. `cadastre fmt` and formatting in the language server: canonical form (line breaks at 100 columns, short blocks on one line, indentation, spacing, alignment of links, single-line declarations, style rules, clauses and trailing comments), comments kept; `--check`
22. GitHub Actions:
   - CI on every push and pull request: generated parser matching `grammar.js` and grammar tests, `cargo fmt --check` (`rustfmt.toml` at 120 columns), `cargo clippy`, `cargo test`, examples valid and formatted, WebAssembly build with clang, VS Code extension
   - releases on version tags: `cadastre` binaries for Linux (static), macOS and Windows, the VS Code extension of each platform with its binary, the WebAssembly module, checksums
   - deployment of the playground to GitHub Pages (WebAssembly module, `web/`, examples), enabled by the repository variable `PAGES` when the repository allows Pages
23. Fixes from modeling a real information system:
   - a relation edge stays bare when `edge_labels` asks for keys it does not have (a cable without `circuit_id`), `relation` to name it anyway
   - a view rule relabeling a rule of the project (same properties, another `legend`) replaces it in the legend
   - `group-by … > on`: a resource on several hosts goes into the outer frame instead of an error, as any multi-valued reference
   - a `device` can be placed in a subnet, with its `ip`, and have interfaces (a Wi-Fi access point in its VLAN)
24. Exact reference of the language, `docs/reference.md`, generated from the grammar (EBNF), the schema (kinds, parents, keys, types, values) and the vocabulary of plans (formats, options, style properties, pseudo-attributes), and checked by `cargo test`; validation and completion read the same tables; the guide, `docs/guide.md` (formerly `syntax.md`), links to it
25. Layout: several frames or nodes on a level of `stack` (`stack: [[a, b], c]`, nested lists in the grammar, accepted only there); `orientation: data` also orients the layout, a `pull` edge drawn from its target to its source (DOT, Mermaid, ASCII art); a warning when `stack` separates the items of a frame
26. Zones: named frames of a view gathering nodes or frames by name or filter, taken out of their `group-by` frames (`zone hostco-sap "Hostco SAP" [hostco-site-east, hostco-site-south] { fill: … }`), designated in `stack` and `cross`; empty `group-by` frames not drawn
27. Documentation split: a compact README, `CONTRIBUTING.md` (building, checks before committing, CI, releases), `docs/design.md` (decisions, architecture, rejected options), `web/README.md` (WebAssembly module, playground), `docs/project-layout.md`, `docs/views.md`
28. Layout: `first` / `last` in a frame (routers above the switches of their room), `routing: curved | polyline | straight | orthogonal`, `edge_labels_layout: free` (labels placed after the layout, `xlabel`), undirected cables and connectors laid out independently of the side declaring them, `cross` written in order with the crossing minimization cut short
29. Edge labels on several lines: `edge_labels_wrap: 40` breaks between values beyond a width, `edge_labels_wrap: values` puts one value per line (DOT, SVG, Mermaid)
30. Small fixes: a warning when a filter of a view matches nothing (style rule, `where` of `edges`, zone filter), with a hint for a `label` used as a name or a short name compared to `name`; `merge_label: count | <n>` summarizes merged edges (`sftp ×9`, the detail in the tooltip); a `database` can run `on` a fleet
31. Table views: `render csv, tsv, markdown { columns: [...] }`, a row per node or per edge (`rows`), columns as keys, pseudo-attributes or paths (`"ancestor(site)"`); CSV and TSV readable by Excel (byte order mark)
32. Checks, the tests of a project: `check` blocks reusing the selection of views (`select`, `edges`, `lift`, `follow`, `where`) with an expectation (`expect none`, `some`, `count <op> N`, `all <predicate>`), a `message` and a `severity`; run by `cadastre check` on a valid model (`--only <name>` for one), shown by the language server and the playground; a failure lists the offending nodes or edges with their positions. `cadastre build --check` for renderings not up to date. The `where` after `lift(…)` filters the lifted edges
33. Series of servers: `for_each (code, ip) in [[lil, 10.1.1.10], …] { … }` declares resources and links once per item, `$code` replaced in names, values and strings, a variable alone keeping the type of the item; `pool` groups servers an app, a job or a database runs `on` (`pool:` on each server, `on: <pool>`)
34. Grouping: a resource goes with the group of what it hosts when all of it shares one (a dedicated server in the frame of its system); frames of values, a free key (`group-by middleware`) or the components of the apps (`group-by component`, `jboss 4.2.0`)
35. `lift` with a path per kind, `via_job: on` beside `via: ancestor(system)?`, so that exchanges inside a system keep a meaning; `follow` relayed by databases, `relay: [database]` or a given one (`relay: [stock.db]`), through the apps reading them, filtered by destination (`relay_to: [app]`)
36. Channels of a broker: the channels are part of the identity of a link (a pull on a topic and a push on another one, to the same broker); `follow` crosses a broker once per channel, in the order of the data (a stream between two topics keeps its steps)
37. Self-hosted playground: `web/build-playground.py` builds a folder holding the page, the WebAssembly module, Graphviz for the browser and the examples, served from any static web server without internet access; the releases ship it as `cadastre-playground-<version>.zip`, and Pages deploys it
38. Size of the WebAssembly module: 1.8 MB to 1.4 MB (465 KB compressed), Tree-sitter built without `std` (no regular expressions for query predicates, unused) and a `wasm` cargo profile optimizing for size
39. Comparing the two ends of an edge in a filter: a path starting with `source` or `target` on the right of a comparison (`source.ancestor(system) != target.ancestor(system)`, `source.version > target.version`); a side without value makes the comparison false
40. Language server: files that are not valid UTF-8 reported as diagnostics at their first invalid byte, as by the command line, the project then not rendered
41. Table views as an HTML page (`render html`, `out/<view>.html`): escaped cells, light and dark themes, the header kept in sight; a Table tab in the playground
42. URLs: a `url` type, checked and without secrets (no password, no `?token=`); `url` (address of a service) and `console` (administration: web console, SSH, RDP) standard keys, opened by a click in SVG and Mermaid, as links in HTML tables and in the hover
43. Filters checked further: order comparisons need a number or a version and a key that can hold one (`hosting > 3`, `version > latest` are errors), the keys of a `select` or `kind` filter must exist for the filtered kinds (`select database where cidr = …`), and `incomplete` on edges (an end or a connector drawn is incomplete)
44. Publishing a project: `cadastre serve` (the project read again at each loading of the page) and `cadastre site` (a static folder, for the continuous integration) show it in the playground, read-only, without the examples; the view, the format and the ad-hoc view (compressed) in the address, to share as a link
45. Egress and ingress: the devices traversed by the flows to and from the internet written once (`egress: [fw01, px01]` on a site, a VPC, a network, a subnet, a system, an app, a job or a database), the nearest one counting, by containment then by `on`; `through` deduced on each flow without one, shown as deduced; `internet` as an end
46. Placement by reference: `parent: dc-alpha.lan.servers` places a resource declared at the root in another one, as if nested (qualified name, lexical scope, inheritance, checks, views), so that the servers of a site or the apps of a system can be split by functional theme; reopening a resource from another file (`extend`) rejected
47. Export to draw.io (`render drawio`, `out/<view>.drawio`): laid out by Graphviz like the SVG (`dot -Tjson`, viz.js in the playground and VS Code), by the compiler without it; frames as containers, edges attached to their ends and routed by draw.io, the shapes, colors and icons of the SVG, the data of each node and edge as draw.io properties; a draw.io tab in the playground and a Save button in the VS Code preview
48. Table views as Excel workbooks (`render xlsx`, `out/<view>.xlsx`): a sheet named after the view, the header bold and frozen, an automatic filter, column widths, URLs as links, ports and steps as numbers; written by the compiler (a zip of SpreadsheetML parts, no dependency), in base64 in the JSON outputs; Download .xlsx and .csv in the Table tab of the playground, Save in the VS Code preview
49. Exports of the whole registry (`cadastre export archimate | graphml | json`, *Export model* in the playground and VS Code): ArchiMate Open Exchange Format (valid against the Open Group schema; element types by kind, relationships as ArchiMate allows them, associations otherwise; properties and documentation), GraphML (nodes and every relation), JSON (resources, containment, resolved references, links)
50. `schedule` of jobs: a cron expression recognized by its shape (five fields, names, macros), checked and shown in plain words in labels, tooltips and hover ("at 06:00 and 18:00 on Monday to Friday"), with the `timezone` of the job or its scheduler; free text kept, the job incomplete until converted
51. Aggregates in filters: `count(path)`, the number of distinct items of a path, compared to a number (`count(on.ancestor(site)) >= 2`), for resilience checks; `count` stays usable as a key
52. Built-in check: the CIDRs of the subnets of a site do not overlap
53. Built-in check: a device of a written `through` is in the site of one end of the flow (a tunnel or a connector: one of its ends), a warning otherwise
54. Impact analysis: `failures`, the resources whose failure alone makes a node unavailable (containment, racks, hosts with redundancy, cluster and pool members, connectors, links and their `through`), for impact views (`where failures has fw01`) and single-point-of-failure checks (`failures.kind = server`)
55. One-off import of a Terraform state (`cadastre import terraform`, *Import Terraform state* in the playground): `.ca` files per site to review, from AWS (VPCs, subnets, instances, gateways, load balancers, EKS, RDS), Azure (virtual networks, subnets, virtual machines) and Google Cloud (networks, subnetworks, instances); the Terraform address in a comment, the resources not imported listed
56. `reach: internet | internal`: what is reached over the internet, inherited along containment then `on` (a SaaS and the internet by default), apart from `scope: external` (outside the perimeter: a directory run by another team, a hosting provider joined by the WAN); `failures(hosting)`, the failures through hosting only, without the links, for single points of failure of the hosting; a key with an argument in paths
57. Databases in a database: `on: <database>` for a database (an instance, a pluggable database or a schema of a shared database), followed to the machine by `group-by on` (frames within frames), `lift` (a target not selected lifted in turn), `failures`; a cycle of `on` is an error
58. Layout of the renderings: `spacing` (a factor of the space between nodes and between ranks, Graphviz and Mermaid), `node_label_size`, `edge_label_size`, `frame_label_size`; `routing: straight` on edges in a style rule, redrawn as straight lines in SVG beside curved ones; the items of a level of `stack` side by side even when edges link them
59. The legend explains the default theme drawn in the view: assumed and doubtful links, triggers, the borders of external, assumed and doubtful resources; a rule with a legend about the same thing names the entry instead
60. Schema of the project: `kind` blocks adding typed keys to the built-in kinds (`string`, `number`, `ref(K)`, closed lists, `pattern("…")`, cardinality, `(required)`) and declaring kinds of the project `like` a built-in one (its parents, keys, icon, shape, groups and selections); keys of the links (`link`, `layer` blocks); a closed list of one value; the descriptive keys left to the schema of the project (`platform`, `technology`, `protocol`, `population`, `role`), declared in the examples
61. Pools by selection: `pool stores { select server where ancestor(site).role = store }`, the members of a pool chosen by the filter of a view rather than a `pool:` on each server
62. Nested zones: `in: <zone>` draws the frame of a zone in the frame of another one, a zone holding only zones (`[]`); an `in` that is not a zone and zones making a cycle are errors
63. Groups of the project: `group storage: database | saas`, a union of kinds, built-in groups or other groups of the project, usable wherever a built-in group is (`select`, style rules, `ref(…)`, checks); conditional constraints stay checks
64. Value types `bandwidth` (`100Mbps`, `"1.5 Gbit/s"`, compared in bits per second) and `spdx` (license expressions checked against the SPDX License List, embedded, with the closest identifier); `license` of apps, jobs, databases, SaaS and components, an SPDX expression; `quantity`, a number and its unit, in the grammar
65. Processes: `process` blocks listing steps in their order (links of the registry, replies, asynchronous calls, processings within a resource, loops, notes), `processes:` on the links serving one; `edges process(…)` in views, numbered as the steps; `render sequence`, a Mermaid sequence diagram; `follow(…, side: [data] | all)`, the calls serving the processing along the way
66. Sequence diagrams: `participants: [..]` on a process, the participants placed first, in this order; the `label` of a step followed by the protocol of its link (`edge_labels: [port]`); `title: false`
67. Renaming in the language server (`textDocument/rename`, F2 in VS Code): a resource renamed with all its references, in the registry and the plans; a qualified name keeps its prefix, a short name stays short, the segment of a renamed system or site changed in the names of its descendants; the new name checked (valid, not taken by a sibling) and the project compiled again before any change
68. Complexity of the language reviewed: one meaning per key (`in:` for the zone a zone is drawn in, `parents:` for the parents of a kind in the schema, `parent:` the placement of a resource, the old forms reported); a tutorial (`docs/tutorial.md`, `examples/tutorial`) in three levels, the registry, views, and further; a table choosing between the edge selectors (`lift`, `follow`, processes)
69. IntelliJ plugin (`editors/intellij`, IntelliJ platform 2024.2 and later): the language server through LSP4IJ (diagnostics, completion, navigation, references, renaming, hover, structure, formatting), the TextMate grammar of the VS Code extension for highlighting, the path of `cadastre` in Settings > Tools > Cadastre
70. IntelliJ plugin on a par with VS Code: the code lenses of the views (Preview, Build) and of the checks (their result, the detail in the Cadastre tool window, its places as links), a live preview of a view in the editors of the IDE (the SVG laid out by Graphviz, the sequence diagrams with the Mermaid plugin, the tables in the HTML and Markdown editors), Build view, Build all views, Export model, Restart language server (Tools > Cadastre), the settings of the diagnostics (incomplete elements, strict); codicons of the code lenses replaced by characters for the clients other than VS Code
71. Participants of a process standing for several resources: `participant esx "ESXi hosts" [prod, esx3]`, its members ends of flows or clusters standing for their servers; a step to or from it designates the link of each member, every one checked; the views draw them all, numbered as the step; one participant in the sequence diagram, its label or its members
72. `layout: elk` (experimental, the `elk` feature): the SVG of a view laid out by Eclipse ELK, its layered algorithm ported to Rust (`merman-layout-elk`, EPL-2.0), and drawn by the compiler like the SVG of Graphviz (shapes and icons of the kinds, styles, links, tooltips, legend); `cross` as the model order kept in each layer, `first` and `last` as layer constraints, `stack` as invisible edges; a warning for `routing` and `edge_labels_layout`; Graphviz without the feature, with a warning
73. Virtual machines: `virtual` before the kind of a machine (`virtual server web01 { on: esx01 }`, `virtual firewall fw { on: prod }`), running `on` a server or a cluster; drawn in its host with `group-by … > on`, stopped by its failure; `where virtual` in views; `on` only for a virtual machine (a warning for load balancers and proxies), `rack` only for a physical one; ArchiMate `Device` or `Node`; cloud instances imported as `virtual server`
74. Network paths deduced from the cabling: in a subnet through the switches whose ports carry its VLAN (`vlan`, `vlans`), between subnets through their gateways (`gateway`, otherwise the routers and firewalls with an interface in them) and the connectors between routers, virtual machines through their host; redundant ways as steps with variants; a `through` deduced on every flow with a complete path (a written one wins, warned about when off the path), the way to the `egress` before it; `edges path(a, b)` drawing the path between two resources (to a SaaS or the internet through the `egress`, from them through the `ingress`), its cables of a port-channel (`aggregate`) as one, with why there is none and the ambiguous gateways; a project key now built in with the same type only warned about
75. `severity: info` for checks: a failure reported as an information, in editors as such and counted apart in the command line (`1 info(s)`), without failing `cadastre check`
76. Project file and modules: an optional `cadastre.toml` found from the directory given and up (`[project]` name, sources, out, strict; `[dependencies]` by path), read by the command line, the language servers and `cadastre serve`; a module brings its schema, registry, styles and checks, not its views, read only (not formatted, not renamed, only its errors reported), transitive, a cycle an error; `for_each … in csv("stores.csv")`, the columns by name, the cells read as values, an empty cell absent, `,` or `;`, errors on their row
77. MCP server (`cadastre mcp [directory]`, `docs/mcp.md`), read only, the project read again at each call: `list_kinds`, `list_keys`, `search_resources` (exact, prefix, substring, label, close spelling), `get_resource`, `list_views`, `check_view` (the diagnostics of a proposed view or check), `eval_view` (nodes, frames, edges, a rendering), `run_checks`; the reference, the cheat sheet for views and the tutorial as resources; results capped at 200 items
78. Before publishing: stability tiers (stable, advanced, experimental), the layout hints of `render` listed apart, a comparison with the existing tools, `cadastre init`, a changelog with the version policy; the SVG follows the dark mode of the page showing it (`prefers-color-scheme`, a style block in the file; the texts on a light fill stay dark)
79. Readable at first sight: the ranks of the SVG computed over the whole view (`newrank`, unless `stack`, `first`, `last` or `cross` steer them) and satellites (`satellites`, a node exchanging with several frames drawn once in each of them, in gray): on the densest view of the retail example, 17 crossings down to 3, the edges 20% shorter, the frames reading by themselves; measured by a script counting crossings and overlaps on every view of the examples
80. `render traversal`: the paths of a view as rows, a row per `path(a, b)` (or why there is none) and a row per step of its processes, from the source to the target through a box at each device traversed (the `through` of its link, written or deduced from the cabling, the other way for a reply), redundant devices in one box, the ends with the machines they run on, the interfaces of the cables (`edge_labels: [interface]`); in the previews of VS Code, IntelliJ and the playground
81. Checks in `.cac` files: a third extension for the tests of a project, apart from the views (`.cav`); a `check` outside a `.cac`, a `view` or a `style` in one, are errors; read by every tool, the completion of a `.cac` proposing `check` only; `cadastre init` creates `src/checks/main.cac`
82. The site of a project for its readers (`cadastre site`, `cadastre serve`): a page per view with its diagram leading to the pages of its resources, a page per resource (facts, links, impact, questions, the views it appears in), indexes by kind, the checks, a search, dark mode and print; the JSON model under `api/` (`docs/api.md`, one model with the export and the MCP server); the playground beside it; `title` and `description` on the views; the diagrams laid out by Graphviz, or drawn in the browser
83. `cadastre anonymize`: a copy of a project with the names of its resources, views, checks, layers and hosts replaced consistently, its strings by texts of the same length, its addresses renumbered, its comments dropped; its kinds, nesting, links, references, plans and schema kept, so that the copy renders the same views: to share a project without exposing it
93. The pairs of failures a redundancy rests on (`failures(pairs)`, *Redundancy* on the site, `failure_pairs` in the API), the most precise ones only
92. The columns and kinds of an export imported in its own words (`cadastre import csv --map … --kinds …`)
91. Several failures together: `failing: [a, b]` in a view or a check, `down` for the resources unavailable then, drawn in red with their legend
90. One-off import of an inventory in CSV (`cadastre import csv`, *Import CSV inventory…* in the playground): a `.ca` file to review, a resource per row of any kind, nested by its `parent` column, its values typed by the schema, what the schema does not know listed at the top
89. Several layouts for the views with `stack`, `first` or `last`: the seven orders, within the ranks the hints fix (`cross` keeps the order written); on the systems view of the `tangled` example with a `stack`, 11 crossings to 1. The site: the boxes of a traversal and the participants of a sequence diagram link to the pages of their resources
88. Several layouts tried: the frames of the root in four orders (as written, reversed, by connectivity, reversed), three of them applied inside the frames too, each with both rankings, fourteen layouts in all, the best drawing kept, a crossing weighed as three average edges: on the `tangled` example, backup 14 crossings to 1, systems 9 to 3, directory 2 to 0, zones 3 to 2 with shorter edges
87. Languages: a catalogue in the core (English the key, French), the language of the project in `cadastre.toml` (`language`) or `--language`, used by the site, the playground published with it, the words of the diagrams and the diagnostics of the compiler (translated when shown, by templates matched on the English, so that a message without a translation stays readable)
86. The site after a reader's feedback on a real project: own renderings (sequence, traversal) shown, info checks apart, variants of a way, what an incomplete resource misses, light home page, views grouped by file, site through `on`, kinds within left out of the index, tables on a phone, plurals; what runs in a site, a subnet, a pool (`runs_here`), the members of a pool, an API page describing the JSON files with live examples; the playground published in a site linking back to it
85. Both rankings tried: Graphviz draws each view with the ranks over the whole view and frame by frame, and the drawing that reads best is kept, measured on the SVG (frames overlapping, crossings, length of the edges); the measure is in the core, for the CLI, the site and the playground alike
84. Twins (`twins`): in a frame, the nodes of one kind with exactly the same exchanges drawn as one box listing them, with one edge per shared exchange, so that a fan of twenty or thirty identical edges reads as one; the `tangled` example, a real model anonymised, with its eight hard views, as the test bench of the layout

## Planned

1. Checks, continued: failures of edges (a cable, a WAN link, a flow), built-in checks (rack capacity, once the height of a server is a key of the schema)
2. Layout in views:
   - `cross` across frames, which Graphviz orders with its own heuristics (frames whose edges are all `layout: free`, levels of zones reversed): computing the order of the frames ourselves, or another layout engine
   - a cycle of flows drawn in the direction of the data crosses itself whatever the order (the lifted view of the `tangled` example, 15 crossings): left out of the ranking (`constraint=false`) they give 48, attached above or below (ports) 19 and 40; another layout engine, or edges routed after the layout
3. Importing from other sources to bootstrap a registry, as one-off files to review: Kubernetes manifests
4. IntelliJ plugin, continued: the `cadastre` executable shipped in the plugin of each platform, as in the VS Code extension; built and checked by the CI; publication on the JetBrains Marketplace
5. `layout: elk`, continued: the edges between frames routed more directly (ELK sends them around the frames, whatever the options of the port), the levels of `stack` kept side by side across frames; the draw.io export laid out by ELK too; deciding whether the releases include ELK
6. Extended network model: routing tables and static routes between routers, layer 2 views of the VLANs
7. Advanced views: ArchiMate diagrams of the views (positions from Graphviz) in the ArchiMate export, logical links through a channel (`bridge`: "B consumes what A produces"), regular expressions in `where`, vendor icons, named themes, manual placement, PNG / PDF exports
8. Extended model: serverless and PaaS, network policies and service mesh, data direction per carried object
