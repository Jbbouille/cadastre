# Cadastre

**Your IT landscape, as code.**

Cadastre is a language and a compiler to describe an information system (sites, networks, machines, applications, flows, data, teams) in readable text, versioned in Git, written by hand by a human or an agent. The compiler draws views from it: SVG, Mermaid, DOT, text, ASCII art, tables; and it tests it against the rules you write.

The idea is that of a land registry (*cadastre* in French): a **single registry** of resources and their relations, from which you draw as many **plans** as you want, without ever rewriting anything.

**Try it in your browser**, nothing to install: [the playground](https://cadastre-lang.org/playground/), and [the sites of the examples](https://cadastre-lang.org/) as `cadastre site` publishes them for their readers.

> Status: 0.x. The language, the compiler, a language server, a VS Code extension and an IntelliJ plugin work on real projects. Until 1.0 the syntax may still change between minor versions, with the old form reported by the compiler; see [Stability](#stability).

## Why

Mermaid and similar tools mix what you describe with how you draw it: a network diagram, a flow diagram and an application diagram are three files to maintain in parallel, and they drift apart. Cadastre separates the two:

1. the **registry** (`.ca` files) states facts: what exists, what contains what, who talks to whom, what goes through;
2. **plans** (`.cav` files) select, filter, group and project those facts, then choose a rendering;
3. **checks** (`.cac` files) state the rules the facts must follow, run like tests.

Compared with what exists:

- **Diagram languages** (Mermaid, PlantUML, D2) draw one diagram per file. Cadastre draws every diagram from one registry, and derives what is not written: the flows between servers from the flows between applications, the path of a data object, the impact of failures, alone or together.
- **Structurizr and the C4 model** are the closest: one model and views drawn from it, elements nested in one another, even relations written with `->`. Cadastre is more of a compiler (typed keys and references, diagnostics, checks run like tests, flows, paths and failures derived, views written as queries), and it is made for the technical map of an information system rather than for software architecture: sites, subnets, racks, firewalls, tunnels, schedulers, SaaS, teams.
- **Terraform and the infrastructure as code** describe what to create in a cloud. Cadastre describes what exists, cloud or not, including what nobody provisions by code; a Terraform state or a CSV inventory can bootstrap it.
- **ArchiMate tools and CMDBs** hold the same knowledge in a database, behind a user interface. Cadastre keeps it in text files: reviewed in pull requests, diffed, blamed, generated by scripts and agents; and it exports to ArchiMate for the tools that read it.

## A quick look

The registry:

```
site aws-paris {
  hosting: cloud
  vpc prod {
    subnet dmz {
      cidr: 10.0.1.0/24
      server web01 { os: debian12 }
    }
    subnet db {
      cidr: 10.0.2.0/24
      server db01 { os: debian12 }
    }
  }
}

data customer { classification: personal }

app billing {
  description: "Monthly invoicing"
  on: web01
  -> crm : https/443 [flow] { carries: [customer] }
}

app crm {
  on: web01
  -> crmdb : tcp/5432 [flow] { carries: [customer] }
}

database crmdb { on: db01, stores: [customer] }
```

<details>
<summary>How to read it</summary>

- **Nesting** with braces expresses the hierarchy (indentation is not significant).
- **Attributes** are always named (`key: value`). Reference attributes, such as `on`, are relations.
- The **arrow** is a flow, with protocol/port, layers in brackets and optional attributes. Inside a block, `-> crm` starts from the enclosing resource; at the root level, write `billing -> crm`.
- One line is one fact: Git diffs stay readable.

</details>

Plans drawn from it:

```
view flows {
  select app, database
  edges  [flow]
  render svg
}

view network {
  select server group-by site > subnet
  edges  lift([flow], via: on)
  render svg
}

view gdpr {
  select app, database, saas
  edges  [flow] where carries.classification = personal
  render svg { edge_labels: [port, carries] }
}
```

<details>
<summary>What they show</summary>

The `flows` view shows `billing → crm → crmdb`, as written. The `network` view only shows servers, grouped by site and subnet: `lift(…, via: on)` lifts the application flows onto the servers hosting them and produces `web01 → db01 : tcp/5432`, **a link that was never written**; the `billing → crm` flow, internal to `web01`, disappears from that view. The `gdpr` view only keeps the flows carrying personal data. Several levels and several points of view, without rewriting anything.

</details>

Checks drawn from it, the tests of the registry:

```
check no-personal-data-in-the-dmz {
  select server
  edges  lift([flow] where carries.classification = personal, via: on) where target.ancestor(subnet) = dmz
  expect none
}

check every-app-has-an-owner {
  select app where not exists(owner)
  expect none
}
```

`cadastre check` fails as soon as a rule is broken, naming what breaks it: `check every-app-has-an-owner failed: 2 nodes selected, none expected: billing, crm` (the registry above has no owner yet).

## Getting started

Install `cadastre` from the [releases](https://github.com/Jbbouille/cadastre/releases) (Linux, macOS, Windows), or build it with Rust:

```bash
cargo install --path compiler/crates/cadastre-cli
# then rebuild the playground beside it, if you publish sites with it (web/README.md)
```

```bash
cadastre init my-system           # a new project: cadastre.toml, src/ with a first site, system and view
cadastre check src                # diagnostics and checks
cadastre check src --incomplete   # what is missing for a complete model
cadastre build src --out out      # every view, to out/
cadastre build src --view flows   # a single view
cadastre build src --check        # renderings of out/ not up to date
cadastre fmt src                  # canonical formatting
cadastre export archimate src     # the whole registry for Archi, Sparx EA (also graphml, json)
cadastre import terraform terraform.tfstate   # bootstrap .ca files from a Terraform state
cadastre import csv inventory.csv             # bootstrap a .ca file from an inventory in CSV
cadastre anonymize src            # a copy with every name, text and address replaced, to share a project without exposing it
cadastre site src --out public    # the site of the project for its readers: a page per view and per resource, search, JSON model
cadastre serve src                # the same site, served and regenerated as the files change
```

SVG requires [Graphviz](https://graphviz.org/) (`dot` on the `PATH`); without it, the DOT source is written instead. In VS Code, the [extension](editors/vscode/README.md) brings highlighting, diagnostics, completion, navigation, formatting and a live preview of the views; its release package ships the `cadastre` executable. IntelliJ IDEA and the other IDEs of the platform get the same language features through a [plugin](editors/intellij/README.md). A [browser playground](web/README.md) runs the compiler as WebAssembly; the releases ship it as an archive to serve from any web server, without internet access.

## Stability

Not everything in the language carries the same promise. Three tiers, so that a project knows what it builds on:

| Tier | What | Promise |
|---|---|---|
| **Stable** | the registry (kinds, keys, nesting, links, references, `for_each`), the schema of the project, views with `select`, `where`, `group-by`, `edges [layer]`, `render` and its formats, checks, the project file and its modules, the command line | kept across versions; a change comes with a deprecation, the old form reported with its replacement |
| **Advanced** | derived edges (`lift`, `follow`, processes), zones, styles, impact analysis, egress and ingress, network paths, exports, the layout hints of `render` | may still be adjusted from what real projects teach; changes are listed in the changelog with their migration |
| **Experimental** | `layout: elk`, the imports (Terraform, CSV), the MCP server | may change or go without notice; built behind a feature, or marked as such in the documentation |
